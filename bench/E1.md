The 1st run of each arrangement cost more than the 2nd: the 1st writes the cache, the 2nd reads it.

**False claims found by reading the answers** (checked against the code):
- **Opus delegating, run 1:** "`tests/order.test.mjs:32` calls `applyCoupon` without passing `today`... the test will start failing on 01/01/2027". **False:** line 32 is `applyCoupon(10000, 'FIRST20', today)`. The information was not in what the researcher returned: whoever decided without reading the full code filled in what was missing.
- **Haiku alone, run 2:** "`x1234567` is accepted because the letters are stripped before the check". **False:** 7 digits are left and the postal code (CEP) is rejected.
- In the answers read from Opus alone (run 1) and Sonnet alone (run 1), no false claim was found.

**Bonus:** every arrangement found a real defect that was not planted: the coupon expiry is compared in UTC (`toISOString`), so in Brazil the coupon expires at 9 pm on the last day.

**Honest reading:**
1. In a small, well-bounded project, even the cheapest model found what mattered. The price difference is huge (97%) and the difference in result was small.
2. Delegating the reading saved a third and doubled the time; and whoever decides seeing only the summary may invent the detail that was missing.
3. The rule that comes out of this: a cheap model to read and raise suspicion; whoever claims "this is wrong" checks it in the code first. Every defect claim needs a `file:line` that someone opened.
4. Small sample (2 runs per arrangement, 1 project): it is a measured case, not statistics.
